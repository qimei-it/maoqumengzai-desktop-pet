# 常驻资源预算

日期：2026-11-17
对应验收项：H-P9-03

## 测量方法

用构建产物（`out/`）启动应用，临时数据目录，未配置任何 Key 与邮箱账户。启动后等 12 秒进入稳定状态，再每 5 秒采样一次，共 10 次，统计主进程及其全部子进程的 CPU 与 RSS 之和。

```sh
MQMZ_DATA_DIR=<临时目录> MQMZ_SCREENSHOT_DIR=<临时目录> \
  node_modules/electron/dist/Electron.app/Contents/MacOS/Electron .
```

采样脚本按 `ps -Ao pid,ppid,%cpu,rss` 还原进程树，只统计该实例的进程。

## 空闲结果（macOS 27.0.1 arm64）

| 指标 | 数值 |
| --- | --- |
| 进程数 | 28 |
| 内存（RSS 合计） | 约 3.8 GB |
| CPU（10 次平均） | 12.5% |
| CPU（去掉单次 40% 峰值后） | 8–10% |
| 数据目录（全新，无用户数据） | 7.6 MB |

采样明细（CPU% / RSS MB）：

```text
7.7 / 3865   10.6 / 3918   8.8 / 3941   10.4 / 3978   40.0 / 3714
12.5 / 3797   9.3 / 3724    8.3 / 3753   8.5 / 3799    8.7 / 3846
```

启动后约 25 秒出现一次 40% 的峰值，对应启动后触发的定时任务（邮箱同步、额度刷新、备份检查与更新检查）。峰值过后回落到 8–10%。

## 结论

**这是首版最需要优化的指标。** 应用启动时会创建约 24 个窗口，每个面板都是独立渲染进程，导致空闲状态下：

- 内存接近 4 GB，对常驻桌面宠物偏高；
- 空闲 CPU 8–12%，会让笔记本风扇与电量明显受影响。

### 主进程指针轮询优化（2026-11-17 已实施）

原来 `pointerTimer` 固定 16ms（60fps）轮询光标，即使桌宠静止、光标在屏幕另一端也照常查询。已改为自适应调度：拖动中、轮盘展开、光标在宠物周围 48px 内时保持 16ms；其余时间降到 64ms；拖动超时或轮盘自动关闭等提前返回的分支也会重新排程。

复测（预热 25 秒后 15 次采样，4 秒间隔）：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 主进程 CPU（中位） | 未单独测量，空闲总 CPU 8–10% | **0.4%**（p90 1.3%） |
| 总 CPU（中位） | 约 8–10% | **5%**（p90 11%） |
| 内存 | 约 3.8 GB | 3.87 GB（无变化） |

结论需要修正：**指针轮询不是主要来源**。主进程已经降到 0.4%，剩下的 8% 与 3.87 GB 几乎全部来自 24 个渲染进程自身（Vue 应用与常驻 CSS 动画）。

因此真正有效的优化是**面板懒加载**：不在启动时创建未使用的面板窗口。

### 面板懒加载（2026-11-17 已实施）

启动时不再创建 13 个面板窗口，只在第一次打开某个面板时创建它自己：

- `createPanelWindows(keys)` 按 key 逐个构造，`ensurePanelWindows(key)` 幂等；
- 每个 `openXxx()` 入口先 `ensurePanelWindows('xxx')`，重复打开复用同一窗口；
- 歌词浮层已随「歌词搬进播放栏」一并移除，不再创建窗口；
- 关闭面板的处理器与 `configurePanelChrome` 只在对应窗口存在时生效；
- 测试与开发诊断用 `MQMZ_EAGER_WINDOWS=1` 保留启动即全量创建，`tests/e2e/lazy-panels.spec.ts` 专门覆盖懒加载路径。

复测（预热 25 秒后 15 次采样）：

| 指标 | 懒加载前 | 懒加载后 |
| --- | --- | --- |
| 启动窗口数 | 23 | **1**（仅桌宠，开发版另有验证台） |
| 内存（RSS 合计） | 3.87 GB | **0.89 GB** |
| 首次打开设置 | 已有窗口，即时 | 新建 1 个窗口，约 200–400ms |

浮层也改为按需创建：置物架、气泡、提示、音量、音符、音乐控制、计时环、眼部在第一次需要显示时才创建窗口，并在各自的 `updateXxxWindow()` 显示条件成立时 ensure。空闲时只剩桌宠一个窗口。

### 浮层懒加载（2026-11-17 已实施）

8 个浮层全部改为按需创建：

- `createOverlayWindows(keys)` + `ensureOverlayWindows(key)`，与面板同一套开关；
- 置物架的 close/blur/focus 处理器改为随窗口创建时挂载；
- 每个 `updateXxxWindow()` 在显示条件成立且窗口不存在时先 ensure，再走原有显示逻辑；
- `setVolumePopup(true)` 与 `showPocket()` 在入口处 ensure。

复测：启动 1 个窗口，内存 **0.89 GB**，空闲总 CPU 中位 **5%**（p90 11%）。

### 关闭即释放（2026-11-17 已实施）

面板关闭后不再只是隐藏：智能体与格式转换这两个大面板在关闭 1.2 秒后被销毁，下次打开重新创建，渲染进程随之释放。1.2 秒的延迟用于避开「刚关就开」的抖动，重新打开会取消销毁并复用原窗口。

保持常驻的是邮件与设置：它们的关闭/重开和数据加载耦合较紧，销毁会带来可见闪烁与状态丢失，暂时保留复用。

同时修正了激活策略顺序：打开面板前先把应用切到 regular，面板才能真正并入本应用的窗口集合（Dock、Cmd+Tab、显示桌面）。

预期：只开桌宠约 0.9 GB；打开设置或邮件后约 1.2 GB；智能体与转换在用完后回落。

### 定时器按到期唤醒（2026-11-18 已实施）

原来的 `focusTick` 与 `bubbleTick` 都固定 1 秒触发，空闲时也在轮询。现在两个循环都改成 `setTimeout` 自调度：

- 番茄钟运行中仍按 1 秒刷新倒计时；空闲时按最近一次喝水、久坐、用眼或待办到期时间唤醒，最长 15 秒一次，用于保持时钟跳变与时区检测灵敏；
- 提醒被更高优先级提醒占用时会排 250ms 重试，不会等到下一次长间隔；
- 所有计时状态变更都经 `persistFocus()` 重新排程，开始、暂停、切换阶段、改间隔、加待办都会立即生效；
- 气泡时钟只在音乐播放时保持 1 秒，其余时间 5 秒；播放状态变化时由 `applyMusic()` 重新排程。

复测（开发版，预热 25 秒后 12 次采样，3 秒间隔）：主进程 CPU 中位 **0.4%**（0.1%–4.0%），与改动前持平——空闲主进程开销主要由 64ms 的光标轮询占据，本次改动减少的是每秒唤醒次数与电量消耗，而不是 `ps` 能看出的平均 CPU。

定向覆盖：`tests/unit/scheduler.test.ts` 验证运行中/空闲/到期/过期/延后重试五种排程结果；`focus-badge`、`recovery`、`todo-reminder-bubble` 三个 E2E 用例重新跑通。

### 格式转换场景（2026-11-18 已量测）

方法：临时数据目录启动开发版，把样例文件写入置物架索引，再通过真实 `convert-open` / `convert-start` 命令走完整转换管线；每 200ms 采样一次应用进程树（主进程 + 渲染进程 + 转换子进程）的 CPU 与 RSS。基线为空闲中位 CPU 5.3%、RSS 928 MB。

| 场景 | 输入 | 耗时 | CPU 峰值 / 中位 | RSS 峰值 | 产出磁盘 | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 图片转 PNG | 12 张 2400×1600 JPEG | 2.77 s | 136.7% / 121.4% | 1251 MB | +122.07 MB | 12/12 |
| PDF 转 PNG | 20 页 A4 PDF | 3.35 s | 113.7% / 110.2% | 1565 MB | +3.92 MB | 20/20 |
| CSV 转 XLSX | 4 万行 × 6 列 | 0.48 s | 103.7% / 103.7% | 1558 MB | +1.28 MB | 1/1 |
| 文档转 PDF | 4000 段 Markdown | 0.67 s | 115.2% / 77.2% | 1821 MB | +0.79 MB | 1/1 |

结论：

- 转换是短时突发型负载，CPU 峰值超过单核（多进程合计），任务结束后回落到空闲水平。
- 图片批量转 PNG 的内存与磁盘增量最大（样例是高熵噪点图，PNG 压缩后仍约 11 MB/张）；普通照片会明显更小。
- 文档转 PDF 的 RSS 峰值接近 1.8 GB，是 Chromium 打印路径的临时开销。
- 转换输出写在源文件旁的 `convert_output/`，磁盘增量等于产出大小；临时工作目录在任务结束后由测试清理。

音乐播放与歌词仍未量测，需要真实播放器与曲目。

### 音乐播放场景（2026-11-18 已量测）

方法：打包版 + 临时数据目录，播放 Apple Music 曲目，每 1 秒采样一次应用进程树，共 20 次；磁盘读取真实缓存目录。

| 指标 | 数值 |
| --- | --- |
| 播放中 CPU 中位 | 10.1% |
| CPU 峰值 | 25.7% |
| RSS 峰值 | 1098 MB |
| 歌词缓存 | 504 KB / 105 首（约 4.8 KB/首） |
| AI 文案缓存 | 108 KB / 27 首（约 4 KB/首） |

四款播放器的接管实测（打包版快照）：

| 播放器 | 读取路径 | 结果 |
| --- | --- | --- |
| Apple Music | AppleScript | 标题、歌手、进度正常 |
| QQ 音乐 | Now Playing helper | `appName` = QQ 音乐 |
| 网易云音乐 | Now Playing helper | `appName` = 网易云音乐 |
| 酷狗音乐 | Now Playing helper | `appName` = 酷狗音乐 |

切换到哪款播放器，就由哪款接管；暂停后保留最后曲目信息，不误报其他播放器。

结论：播放场景 CPU 中位约 10%、峰值约 26%、RSS 约 1.1 GB；磁盘只有歌词与 AI 文案 JSON，单曲约 8–10 KB。
